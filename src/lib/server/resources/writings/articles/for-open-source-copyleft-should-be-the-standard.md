# For open source, copyleft should be the standard

In open source development, it’s common for the maintainers of software to adopt a conventional license for the community. In [Node.js](https://nodejs.org), [MIT License](https://choosealicense.com/licenses/mit) and [Apache License 2.0 (“Apache License”)](https://choosealicense.com/licenses/apache-2.0) are popular; in [Clojure](https://clojure.org), [Eclipse Public License 1.0 (“EPLv1”)](https://choosealicense.com/licenses/epl-1.0) is popular; in [Rust](https://rust-lang.org), dual licensing is popular, so it’s common for MIT License and Apache License to be options. This process makes sense because it’s often in the community’s interests to maximize compatibility. I used to license the software I developed like this, but have since adopted copyleft licenses like [GNU Lesser General Public License v3.0 (“LGPLv3”)](https://choosealicense.com/licenses/lgpl-3.0) and [GNU General Public License v3.0 (“GPLv3”)](https://choosealicense.com/licenses/gpl-3.0).

A lot has been said on this topic[^1][^2], but I specifically want to cover it in the context of self-discipline. The MIT License and Apache License are considered permissive because they impose minimal conditions. This is great for users because almost anyone can use it, but can cause issues from it enabling people to subvert the open source process. For example, it’s legal for maintainers to switch from such a license to a non-open source one, against the will of other contributors and users. The most notable incident I’m aware of this happening is [the Redis database](https://github.com/redis/redis) switching from [BSD 3-Clause “New” or “Revised” License (“BSD License”)](https://choosealicense.com/licenses/bsd-3-clause) to dual licensed under [Redis Source Available License 2.0 (“RSALv2”)](https://redis.io/legal/rsalv2-agreement) and [Server Side Public License (“SSPL”)](https://www.mongodb.com/legal/licensing/server-side-public-license). While the SSPL is considered copyleft, [it’s not considered open source](https://opensource.org/blog/the-sspl-is-not-an-open-source-license).

I consider this a reflection of the state of open source. [The benefits are primarily one-way and directed at users](https://opensource.org/osd), while maintainers are expected to foot the bill in return for an acknowledgment. I think it’s due to this disconnect in how open source works that incidents like Redis could’ve occurred. If the benefits were instead two-way, developers could expect a stronger open source process, even in the event of people being evil.

[There are organizations like the Free Software Foundation that have debated open source](https://www.gnu.org/philosophy/open-source-misses-the-point.html) and arrived at [free software](https://www.gnu.org/philosophy/free-sw.html), but I think the answer is specifically [copyleft](https://writefreesoftware.org/learn/copyleft) as an alternative to permissive licensing. Unlike the latter, the former imposes conditions on sharing the software that affect both users and maintainers. For example, a user modifying copyleft software is required to use the same license, if not a stronger variant, while a user distributing it as part of a wider work is required to use a compatible license. The most common copyleft licenses I’m aware of are [Mozilla Public License 2.0 (“MPLv2”)](https://choosealicense.com/licenses/mpl-2.0), LGPLv3, GPLv3 and [GNU Affero General Public License v3.0 (“AGPLv3”)](https://choosealicense.com/licenses/agpl-3.0).

This solves the issue of someone creating a non-open source fork (and would’ve thwarted Redis’s plans), but still allows maintainers to use a non-open source license in the event that they relicense the software with permission from the copyright holders (i.e., the contributors). For projects like [mpv](https://mpv.io) with hundreds of contributors, this is impractical. For software developed with next to no external contributors, or whose contributors have signed a contributor license agreement (CLA), this is a real possibility. The most that can realistically be done is to pick up stewardship, [which is what the Linux Foundation did with Valkey as an alternative to Redis](https://www.linuxfoundation.org/press/linux-foundation-launches-open-source-valkey-community), since previous versions continue to be available under the original license. I will note, relicensing to another open source license is not always impractical, as mpv partially relicensed from [GNU General Public License v2.0 (“GPLv2”)](https://choosealicense.com/licenses/gpl-2.0) to [GNU Lesser General Public License v2.1 (“LGPLv2.1”)](https://choosealicense.com/licenses/lgpl-2.1).[^3][^4]

Now, I won’t sit here and act like I know what it’s like to maintain a large, open source project, but what I do believe is that open source as a process requires a lot of self-discipline to be sustainable in the long run. I’ve mentioned Redis several times here, but obviously not every user base experiences such a rug-pull. In my opinion, the value of copyleft comes from balancing expectations. For users, it ensures that the software is unlikely to be compromised. For maintainers, it ensures that contributions remain open. A lot of developers will insist that licenses like GPLv3 and AGPLv3 are harmful and reduce maintainers’ prospects of mass adoption, but software is typically written for a certain audience, [and open source is not about any one of us](https://gist.github.com/richhickey/1563cddea1002958f96e7ba9519972d9).

To close, I think it’s important to note that copyleft exists on a spectrum and can be grouped into weak copyleft, which is limited to the licensed code itself, and strong copyleft, which extends to the work that uses it. The former permits surrounding code to keep its own license, while the latter doesn’t. Because of this, it’s generally safe to distribute libraries under weak copyleft licenses like MPLv2 and LGPLv3. I see very few reasons for maintainers not to adopt them.
